# Visual documents (Visual Blueprint P0)

Studio and the print view draw purpose-built visuals from one semantic view model instead of generic text cards. This first slice has one framework: the **business model canvas**.

Core: `packages/brand-core/src/visual/` (`@brand-os/brand-core/visual`). Studio: `apps/studio/src/views/visual.ts` (renderer), `views/visual-page.ts`, `routes/visual.ts`, `static/visual.css`, `static/visual.js`. Tests: `tests/visual-bmc.test.ts`, `tests/studio-visual.test.ts`, `tests/studio-visual-browser.test.ts`.

## Rules

- **One truth path.** The canvas is built through `documents/model.ts` `itemFor`, exactly like the Brand Book: approved facts, labelled owner drafts, missing answers, restricted values withheld. The public edition shows only approved, public, published facts. There is no new store and nothing is written.
- **No invented content.** A zone with no question (key activities, key resources) is a designed gap; the proposed question id is listed under **Details and sources**. Links between segments, offers, channels and revenue are not drawn, because the bank stores one prose answer per field (`relationships.modeled: false`).
- **Language-neutral document.** Values stay as approved and are never translated. Labels, prompts and states come from `visual/i18n.ts` (en/fa/tr). The canvas keeps its canonical left-to-right topology in Persian; text inside zones is right-to-left.
- **Claims.** The framework reference says *informed by*, with the licence status under review. Nothing says certified, compliant or official. The layout is original Brand OS geometry, not Strategyzer artwork.
- **Screen and print from the same document.** The print view (`/strategy/business-model/print`; `/visual/print` redirects since V2.4) is a static A3-landscape composition: page one the canvas, page two sources, states, framework and next questions. Saved as PDF from the browser. Not labelled print-ready: no bleed, colour profile or PDF/X claim.
- **Golden examples** use the fixture in `visual/fixtures.ts`, stamped ILLUSTRATIVE / MOCK DATA on every page and never read from or written to a brand. `npm run visual:golden [-- --out dir] [--no-pdf]`.

## Renderer registry, primitives and framework registry (V1.1)

- **Renderer registry** `apps/studio/src/views/visual-registry.ts`: one renderer per `VisualBlock['type']`, typed so a new block type without a renderer fails the type check. Compositions call `renderBlock`.
- **Shared primitives** `apps/studio/src/views/visual-primitives.ts`: state chip, legend, ghost geometry (`lines`, `swatches`, `specimen`, `mark`), source footnote (plain label, version, date; never a field id), topology mini-map. Every block uses these instead of its own copy.
- **Framework registry** `packages/brand-core/src/visual/frameworks.json` (template-owned, bundled into the production Studio image) with `schemas/framework-registry.schema.json`. `npm run validate` checks the schema and the claim rules (`visual/framework-registry.ts`): no `externally_certified`; `aligned_with` / `verified_against` need `verified_on`; `original_professional_template` only for Brand OS layouts; no certification or compliance wording. Metadata only, never a fact. Renderers read the copy that ships with the template code (`frameworkRef(id)`).

## Brand Book "Visual identity" chapter (V2.1)

`visual/identity.ts` builds a `visual_identity` document from three facts and the asset manifest: `brand.color.roles`, `brand.type.scale`, `brand.logo.min_size`, plus the master asset. Rules:

- **Approved only.** A plate is drawn from an approved fact (or approved and past review, labelled stale). A draft or withheld value is not even carried in the document (`value: null`); the plate shows the designed "awaiting approved asset" page with the reason and, for the owner, the next step.
- **Master asset.** The logo plate needs an approved (status `approved`/`published`), checksummed, previewable, non-example manifest asset tagged `logo` (published, for the public edition). Template example placeholders and draft-status files never count. Which one is the master is resolved in this order, never guessed: (1) an asset named in the approved `brand.logo.masters` answer by its exact asset id or exact manifest `path`/`preview` (whole-token match; first named wins); (2) an asset tagged `master`; (3) the only approved logo; (4) a light/dark pair (see *Logo system* below). Several approved logos with none named, tagged or paired give the designed `ambiguous` state, which asks the owner to name the master in `brand.logo.masters` or tag it. Status is authoritative: a `draft` tag on an approved file does not block it, but the internal edition shows "Tagged draft" (and "Internal · not published" when it is not published) next to the master; the public edition never does. The investor profile follows public (owner decision 2026-11-24): a published master still tagged `draft` is drawn without any mark; an unpublished one tagged `draft` is not drawn. The file is shown through the existing asset route; its proportions come from the SVG viewBox or PNG header, otherwise a square frame is drawn and the note says so.
- **Logo system (BOS-16).** Which file is the master is resolved in this order, never guessed: (1) an asset named in the approved `brand.logo.masters` answer by its exact asset id, its exact manifest `path`/`preview`, or a bare file name that belongs to exactly one offered asset (whole-token match; first named wins); (2) an asset tagged `master`; (3) the only approved logo; (4) a light/dark pair: exactly two approved logos, one for light and one for dark backgrounds, form one system and the on-light file is the master (`resolved_by: pair`). Anything else with several approved logos stays `ambiguous`. Around the master the block carries `system: { on_light, on_dark, icon }`: the file for light backgrounds is drawn on a white plate, the one for dark backgrounds on a near-black plate, and the icon at favicon (16, 32, 48 px) and avatar (96, 160 px) sizes. Roles come from manifest tags first (`on-light`, `on-dark`; `icon`, `mark`, `logomark` or `favicon` for the icon), else, for a file tagged `logo`, from the documented file-name convention (`dark`/`black` is dark ink for the light plate; `light`/`white`/`reversed`/`inverse`/`negative` is light ink for the dark plate; both or neither gives no role). The internal edition says when a role came from the file name and how to confirm it with a tag. Each file needs the same eligibility as the master (approved, checksummed, previewable, not an example; published in public), shows the same `draft_tag` / `internal_only` badges, and is dropped in the public and investor profiles when it is unpublished and tagged `draft`. When the state is `ambiguous` or `not_previewable` the owner's view lists the approved candidate ids and the one-line fix (en/fa/tr). The Brand Book's logo chapter is capped at *Partial* while no master is drawn (`logoChapterStatus`), so it is never *Complete* with an empty logo slot. Studio caches built under an older rule rebuild (`IDENTITY_MASTER_RULE` 3).
- **`brand.logo.masters` is machine-read.** The question asks for the asset id or the full manifest path. When an answer is recorded (`brand:interview --question brand.logo.masters`, `logo_masters` in `--json`), before it is approved (`brand:approve`, on stderr) and in `npm run validate` for the approved answer, `checkLogoMastersReference` warns when it names no exact id or path and lists the matching ids (bare file names are matched too), else every real logo and icon. A warning never blocks. A brand repository whose question bank still has the earlier prompt gets a validate warning, not a drift error.
- **Measured contrast.** Ratios are computed with the WCAG 2 formula (`@brand-os/design-tokens` `contrastRatio`), compared exactly, displayed rounded down. Combinations are only those the role names declare (`onPrimary` on `primary`); the grid measures every pair up to ten colours. A ratio is not an accessibility audit.
- **Type.** Specimens are SVG text at true CSS-pixel size. A family Studio bundles (Inter, Rajdhani, Vazirmatn, all OFL) is drawn with the bundled file; other families render if installed on the device, otherwise the fallback. Persian lines fall back to Vazirmatn.
- **Layout.** Editorial book: chapter opener with contents, numbered plates, hairline rules on screen. The print view is the V1.2 book (below).

## Print engine (V1.2)

Profiles are typed in `packages/brand-core/src/visual/print-profiles.ts` (`PRINT_PROFILE_SPECS`): `book_a4_portrait` (ready), `canvas_a3_landscape` (ready, the canvas print view, unchanged), `deck_16_9` (planned: geometry only; the export command refuses it).

- **Book, `book_a4_portrait`** (`apps/studio/src/views/visual-print-book.ts`, styles in `static/visual-book.css`). The renderer lays out every page itself, so Chrome prints exactly one PDF page per sheet and the contents carry real page numbers. Page 1 cover, page 2 imprint (brand, edition, facts-as-of date, source commit, format, typefaces, the approved-only rule and the no-certification note), page 3 contents (number, title, dotted leader, page). Then one section per plate, each on a new page, and the sources-and-framework appendix. Running heads: classification at the inner edge, book title on verso pages and the section title on recto pages at the outer edge; folios on the outer edge. Persian mirrors the whole book (binding on the right) and uses Persian digits for folios; canvases stay canonical.
- **Flows.** Content is a list of flows: blocks that never split (a plate head, a row of swatches, a type role, the logo plate) and tables that split between rows (contrast grid, sources) with the header repeated, a "continued" caption and a "continues on the next page" line. Headings are kept with the first piece of what follows. A plate's source line becomes a numbered note at the foot of the page that carries its reference (`IdentityContext.note`); a page is never created for notes alone.
- **Heights.** Studio's print view paginates with built-in estimates (calibrated from Chrome measurements with a few millimetres of slack). `npm run brand:export-visual` measures every flow in a Chrome galley first and paginates with the measured heights, then prints and checks every page for overflow.
- **Export command.** `npm run brand:export-visual -- [--doc identity|bmc] [--lang en|fa|tr|all] [--edition internal|public] [--out dir] [--fixture] [--no-pdf]`. Writes `<doc>.<edition>.<lang>.html` (fonts and the approved master embedded, opens offline) and `.pdf` when Chrome is found (`CHROME_PATH`). Default folder `dist/visual-export` (git-ignored). It reads through Studio's projection, so drafts are not carried and restricted values stay withheld, and it refuses output inside `brand/` or a `.private` folder (also through a linked folder or parent, checked on the real path before and after the folder is created, and it never writes through a link left in place of an output file), refuses to run under an agent token and refuses an HTML that looks like it carries a credential. The export reads the working copy: when `brand/` has uncommitted changes it says so, and the imprint prints "plus changes in brand/ not yet committed" next to the commit. When the measuring pass fails it says so and paginates with the estimates (the overflow check still runs). Studio never writes files.
- **Not claimed.** The PDF is a browser PDF: no bleed, crop marks, colour profile or PDF/X claim.
- **Two A4 paths.** Only the Visual identity chapter uses this engine. The competitor (V2.2) and mascot (V3.4) print views still use the earlier `.vz-page--book` page in `visual.css` (browser fragmentation, no folios): those rules are live, not leftovers, and must stay until those views move to the engine.

## Visual QA (V1.3)

`tests/studio-visual-qa.test.ts` runs in the Studio (Chrome) CI job (`npm run test:studio`) on the ILLUSTRATIVE / MOCK DATA fixtures only. It needs no npm dependency: the PNG codec, pixel diff and PDF reader are in `tests/helpers/visual-qa.ts` (Node `zlib` only).

- **Reference screenshots.** The fixtures are rendered through `brand:export-visual` (HTML, built-in heights, so the layout does not depend on a measurement) and captured in print media: the A3 Business Model Canvas page and the A4 book cover, contents and colour plate, in en and fa. Before a capture the test waits for every font face (a face that fails to load fails the test), turns animation and transitions off and asks for reduced motion; Chrome runs with hinting, LCD text and sub-pixel positioning off and an sRGB profile. Chrome also gets a fontconfig that sees only the Liberation fonts (`fonts-liberation`, a dependency of the google-chrome package), so a system fallback font cannot move a line: before this, the Persian pages differed by about 3 % between two Linux machines with the same Chrome. Baselines are in `tests/visual-baselines/` as PNGs averaged over 2 × 2 blocks (15–90 KB each).
- **Threshold.** Both images are averaged over 2 × 2 blocks; a pixel counts as changed when one channel moves by more than 48 (of 255); a page fails when more than 0.3 % of its pixels changed. A capture that misses is taken once more before failing, so a frame caught mid-paint under load is not a failure. A one-line wrap, a moved margin or a missing block is far above the limit (a 5 mm margin swap moves 3.3 %).
- **On a mismatch** the failure names three files in `dist/visual-qa/` (or `VISUAL_QA_OUT`): `<name>.actual.png`, `<name>.baseline.png` and `<name>.diff.png` (baseline faded, changes in red). In CI they are uploaded as the `visual-qa-diff` artifact.
- **Updating baselines.** Only for an intended visual change: `npm run visual:baselines` (needs a local Chrome; it overwrites `tests/visual-baselines/*.png`). Look at every changed image (`git diff --stat tests/visual-baselines`) and commit them with the change that caused them. Make baselines on Linux with the Chrome CI uses; macOS or another Chrome major version rasterises text differently and can exceed the threshold.
- **Digital PDF.** The book is exported by the V1.2 path (measured two-pass layout) in en and fa and read back: A4 pages, cover title and the ILLUSTRATIVE stamp present, every contents entry present with the page number of the page that prints that section, every page from the contents on carries its folio (Persian digits in fa), every font in the file is embedded (Chrome embeds the variable Inter and Vazirmatn as Type 3 glyph programs), Inter, Rajdhani and Vazirmatn among them, and every Persian page set in Vazirmatn. System fonts that also end up in the file (the monospace face for hex codes, a fallback for arrows) are reported, not failed. No bleed, crop marks or PDF/X: not claimed.
- **RTL.** fa pages have `dir="rtl"` and `lang="fa"`. No heading overflows its box or page, and no word in a heading is split across lines (checked per word with DOM ranges). Book contents run page number, leader, title from left to right in fa (the reverse in en) with Persian digits; folios sit on the outer edge (recto left in fa). The canvas keeps the canonical left-to-right zone order in every language and its grid and legend fit the A3 page.
- **Known finding (todo test).** On the fixture, the canvas print footer line is pushed about 7 mm below the fixed A3 page and clipped (mock banner plus long fixture text). Real Studio data fits. The `todo` test turns green when the canvas print layout is fixed.
## Mascot atlas and six-stage evolution sheet (V3.4)

`visual/mascot.ts` builds a `mascot_atlas` document (blocks `mascot_atlas`, `mascot_evolution`) from `brand/mascot/catalog.yaml`, `brand/mascot/stages.yaml` and the asset manifest. Nothing is generated, traced or inferred. Rules:

- **Approved artwork only.** A state or stage is drawn only when the catalog row and the artwork variant are `approved`/`published` and the asset is approved, checksummed, previewable and not a template example. The file is shown through the existing asset route. Usage, do and don't notes travel only with a drawn state.
- **Drafts.** Artwork that is `created`/`reviewed` (or approved artwork on an unapproved row or asset) is never drawn. The internal edition names the state under "Not yet drawn" with "Artwork in review, not approved"; the public edition does not mention it.
- **Public edition.** Needs the artwork and the row `published`, the asset published (publication policy), and no `draft` tag on the file. A draft-tagged file stays hidden from public view until it is published without the tag; the internal edition shows it with "File still tagged draft" and "Internal only, not published". The investor profile follows public: draft-tagged artwork is not drawn there either.
- **Evolution sheet.** Stages in `order`, at least six frames; frames past the recorded stages are "Not defined" placeholders. A stage's picture is approved artwork recorded for that stage id (front angle first, then catalog order, then artwork id). The template's `configuration: example` stages are labelled "Example configuration" internally; in public, only approved stage names are shown.
- **Module off.** `modules.mascot.enabled: false` gives a designed "module is off" plate; nothing is read.
- **Studio.** `GET /brands/<slug>/brand/mascot[/print[?edition=public]]` (V2.4 stable path; the old `/visual/mascot` path answers 301), linked once from the Assets page's mascot card. Ids (state, artwork, asset, stage) are only in the details disclosure and the print appendix. Print uses the earlier A4 portrait page (`.vz-page--book` in `visual.css`) on the browser print path, not the V1.2 print engine: no imprint, contents page numbers, running heads or folios.
- **Registry.** `MASCOT-MODEL-SHEET` (`original_professional_template`, Brand OS layout). Fixture: `illustrativeMascotAtlas` (ILLUSTRATIVE / MOCK DATA; mock artwork is a labelled frame, not a character), in `npm run visual:golden`.

## Adding a visual

1. Add a block type to `visual/model.ts` (additive; bump nothing unless an existing field changes meaning).
2. Build it from existing facts through `itemFor` (or another existing projection). If it needs data Studio cannot see (anything under `brand/.private`), it is not a Studio visual yet.
3. Add the framework to `packages/brand-core/src/visual/frameworks.json` if it cites one. Add en/fa/tr text, a renderer registered in `views/visual-registry.ts` (built from `visual-primitives.ts`), an illustrative fixture and tests for every state, and a browser check at five widths plus a printed PDF.

## Reading layer

The canvas cells carry only the reading: standard zone title, the canonical prompt and the entries with their state. Question ids, next questions, related answers, the edition note, the framework and the links note sit in a closed **Details and sources** disclosure under the canvas on screen, and on page 2 of the print view. Page 1 of the print view carries no technical id.

## List questions and canvas links (V3.1, owner decision D3)

Four Business Model Canvas zones now have list questions (`question_type: repeating_entity`): `business.model.segments`, `business.model.key_activities`, `business.model.key_resources` and `business.model.cost_items` (module `business-company`, optional, internal). Core: `packages/brand-core/src/entities.ts` (item specs, validator, operations), `entity-migration.ts` (legacy answers). Tests: `tests/repeating-entity.test.ts`, `tests/repeating-entity-readers.test.ts`, the V3.1 cases in `tests/visual-bmc.test.ts` and `tests/studio-visual.test.ts`.

- **Storage.** The ledger stores one canonical JSON string per list (`brand-os.entity-list/1`): `question`, `next`, and `items` with `id`, the spec's fields and optional `links`. Normalizing it again gives the same string, like the other structured types. `ENTITY_SPECS` is the one definition of the fields; the question bank carries a summary (`entity:`).
- **Fields.** Every item has a `name` (required, ≤120), a `detail` (≤400) and one standard choice: activity type (production, problem solving, platform or network), resource type (physical, intellectual, human, financial), segment priority (primary, secondary, exploring), cost behaviour (fixed, variable, mixed). Labels are en/fa/tr; item text is never translated. Cost items refuse money amounts in any script; amounts stay in the restricted `business.finance.costs`.
- **Ids and links.** Ids are `act-`, `res-`, `seg-`, `cost-` plus a number. Editing or moving keeps the id; `next` only grows, so a removed id is never reused and a link to it stays visibly unresolved. Activities may link to segments and resources, resources to activities, cost items to activities and resources. Offers, channels and revenue streams are still prose and are never linked.
- **Editing.** `npm run brand:interview -- --question <id> --entity add|edit|move|remove|list` (`--field key=value`, `--links id,id|none`, `--position N`, `--item <id>`, `--json`), or answer the whole list with `--answer` (one item per line or `;`: `name | detail | choice | links: seg-1`; an item keeps the id of the earlier item with the same name, or write `seg-2:` in front). Every write is a draft; on an approved list it is a pending change proposal (`brand:approve -- --ids chg-…`). The last item cannot be removed: "none" is `not relevant` or `unknown`. Studio stays read-only and shows the merged lists.
- **Legacy values.** A stored value that is not a canonical list is kept exactly as written and flagged (documents, Studio, canvas). `npm run brand:migrate` converts text that reads as a list: a draft becomes a `system` draft (the original text stays as its raw answer and in the superseded record); an approved fact is not touched and gets a change proposal instead. Text it cannot read as a list is reported by id and left alone. Running it again does nothing new.
- **Canvas.** List items fill their zone in the owner's order with their choice labels; a link reads as the target item's name, or "an item not shown in this edition" when the target is not visible (removed, unanswered, unpublished). A list zone with nothing visible shows a designed empty state. The links panel (Details and sources, print page 2) lists recorded links by zone and item name; `relationships` is `{ modeled: true, links }`, or `{ modeled: false, reason: 'no_list_items' }`. Item ids stay out of the main view.
- **Readers.** `brand_retrieve` returns an approved list with its items in `meta.entity` (drafts never). The Coach reads list questions by id and quotes no item. Task Context packs do not read list questions yet.

## SWOT / TOWS and the Value Proposition Canvas (V3.2)

Built on the V3.1 list questions. Core: `packages/brand-core/src/visual/strategy-lists.ts` (`buildSwotTows`, `buildValueProposition`, the composers `swotTowsDocument`, `valuePropositionDocument`), text `i18n-strategy.ts`, fixtures `fixtures-strategy.ts`. Renderers: `apps/studio/src/views/visual-strategy.ts`, pages `visual-strategy-page.ts`. Tests: `tests/visual-strategy.test.ts`, `tests/studio-visual-strategy.test.ts`.

- **Questions.** `business.swot.strengths` (`str-`), `weaknesses` (`wk-`), `opportunities` (`opp-`), `threats` (`thr-`) with a confidence choice (evidenced, owner's view, hypothesis); `business.swot.tows` (`tows-`) with a type (SO, ST, WO, WT) and links to SWOT items; `business.fit.jobs` (`job-`), `pains` (`pain-`), `gains` (`gain-`), `products` (`prod-`), `relievers` (`rel-`), `creators` (`gcr-`). All optional and internal.
- **Link rules.** A TOWS type narrows its targets: SO → strengths and opportunities, ST → strengths and threats, WO → weaknesses and opportunities, WT → weaknesses and threats. A strategy without a type may link to any SWOT list and is drawn under "Strategies without a type", never placed in a cell. Relievers link to pains (and products), creators to gains (and products); jobs, pains, gains and products may link to customer segments.
- **Sources.** Items of these lists take `sources` (at most eight): an answer id (`business.offer.summary`), a knowledge note (`kn_…`), an evidence record (`ev-0001`) or an `https://` page without user name or password. In a line: `name | detail | choice | links: … | sources: …` (either order). The reader numbers them in reading order: an approved answer by its label (never its value), a shared note by its title (an idea, not a fact), evidence by status, a web page by host (origin and path only; query and fragment are dropped). Anything not visible is "Not available in this edition". The public edition keeps approved answers and web pages only and counts the rest.
- **Fit.** Each pain lists the visible relievers linked to it, each gain the creators. The page says "2 of 3 pains have a linked reliever"; there is no score and nothing is matched by wording.
- **Layout.** Standard topologies, canonical in every language (the grid is LTR, the text inside follows the locale): SWOT 2×2 with the internal/external and helpful/harmful axes; TOWS with S and W columns, O and T rows (Weihrich); the value map square (products and services, gain creators, pain relievers) beside the customer profile circle (gains, pains, customer jobs). Empty quadrants and zones are designed gaps. Ids stay in the details disclosure and the print appendix.
- **Print.** A4 portrait: opener, SWOT, TOWS (or the canvas, then the fit on its own plate), then sources, ids and framework. Six items per SWOT/TOWS area and four per canvas zone on the plate, "+N more", the full list in the appendix. Folios come from the page margin (`@page vz-sbook`, `vz-sbook-fa` with Persian digits).
- **Registry.** `SWOT`, `TOWS`, `VPC` in `frameworks.json`, all `informed_by`. The canvas layout is an original Brand OS drawing, not Strategyzer artwork.

## Customer journey swimlane, SOSTAC overview and OKR tree (V3.3)

Core: `packages/brand-core/src/visual/plan.ts` (builders), `model-plan.ts` (blocks), `i18n-plan.ts`, `fixtures-plan.ts`; list specs in `packages/brand-core/src/entities-plan.ts`. Studio: `views/visual-plan.ts` (renderers, sources, ids, A3 print), `views/visual-plan-page.ts`, `routes/visual-plan.ts`. Tests: `tests/visual-plan.test.ts`, `tests/studio-visual-plan.test.ts`.

- **Data.** `business.marketing.journey_stages` (stages in owner order; lanes touchpoints, actions, emotion, pains, opportunities; evidence; links to segments), `business.goals.objectives` and `business.goals.key_results`. A key result always has a target number, a unit and the source system that measures it; `current`, `baseline` and `measured_on` are optional. Units that are currencies are refused (money is restricted finance). A key result links to one objective.
- **No invented numbers.** Progress is `(current − baseline) ÷ (target − baseline)`, only when both are recorded; without a baseline the card says "No baseline" and draws no bar (a key result may go down, so zero is never assumed). A missing current value is "Not measured yet". Targets are labelled as plans.
- **Links.** A stage's segments and a key result's objective read as names when visible in the edition; otherwise "an item not shown in this edition" / "Objective not shown in this edition". Key results without a visible objective are listed apart, never moved under another objective.
- **SOSTAC.** Six stages in canonical order (`SOSTAC_SPECS`): each lists the existing answers that speak to it (Objectives also shows the OKR objectives list, Control the key results). The restricted marketing budget is never read. SOSTAC® is a registered trade mark of PR Smith; the overview is an original Brand OS layout, `informed_by`.
- **Direction.** The swimlane is a table and the tree uses logical CSS, so both follow the page direction: in Persian stage 1 and the tree root sit on the right, the emotion curve and progress bars are mirrored. SOSTAC reads in the page direction; its letters stay Latin (a standard name). Numbers, versions, list counters and folios use the page's digits.
- **Print.** A3 landscape on its own named page (`@page vz-plan`, no margin counter): page 1 the visual, page 2 sources, framework and (internal edition) ids and next questions. Studio's print view is `/print` (internal edition). These pages are views of the marketing plan (journey, SOSTAC) and the business plan (OKR), which the V4.1 public profile never receives (`PROFILE_DOCUMENTS`), so Studio offers no public edition and `?edition=public` answers 404 (`visualProfilePermits`). The core builders still produce a public edition (approved and published only) for tests and the illustrative golden files.

Core: `visual/audit.ts` (module catalog, rubric, checks, gate), `visual/i18n-audit.ts` (en/fa/tr report text), `visual/pilot.ts` with `visual/fixtures-pilot.ts` (two synthetic brands), policy `visual/release-gate.json`. Command: `scripts/visual-audit.ts`. Tests: `tests/visual-audit.test.ts`. V3.1 (structured BMC list zones) merged inside the Business Model Canvas, so it is scored there, its `i18n-entities.ts` catalog included. V3.2 (`swot_tows`, `value_proposition`) and V3.3 (`customer_journey`, `sostac_overview`, `okr_tree`) are scored as modules of their own.

```
npm run visual:audit [-- --lang en|fa|tr] [--json | --md] [--out file] [--pilot]
npm run visual:gate  [-- --release] [--lang en|fa|tr] [--pilot]
```

Read-only on the checkout. `--out` refuses `brand/` and any `.private` path. `--pilot` builds the synthetic brands in a temporary folder with a throwaway data key and removes it.

### The 0–5 rubric

A module scores the highest level whose checks, and every lower level's checks, all pass. Every check runs on the checkout; a check that cannot run fails, and the report gives the evidence for each one (file, test count, catalog counts, gap count, citations).

| Level | Name | Checks (all must pass) |
| --- | --- | --- |
| 0 | Not built | builder or core tests missing |
| 1 | Model | `model`: the builder file exports the declared builder; `core_tests`: every declared core test file exists and has tests |
| 2 | Languages | `i18n`: every English string key is in fa and tr, no empty string, ≥ 90 % of fa strings in Persian script |
| 3 | States | `empty_state`: a fixture built and found to carry designed gaps (missing, awaiting, unavailable, not drawn), or a named test asserting one; `studio_tests`: Studio renderer test files exist and have tests |
| 4 | Publication-safe | `print`: a test exercises the print view (n/a for a screen such as the Publishing gallery); `rtl`: a test asserts the Persian page is right-to-left; `redaction`: public modules: the public fixture in en/fa/tr carries no value in a draft, withheld or other non-approved state, no draft or internal badge, no fixture sentinel, and the V4.1 redaction test builds this module's public edition; internal modules: the public profile refuses the document type |
| 5 | Release-grade | `visual_qa`: en and fa reference screenshots in `tests/visual-baselines` used by `tests/studio-visual-qa.test.ts`; `standards`: every framework the module's output cites is `verified` in the registry (n/a when it cites none) |

Public modules are the document types the V4.1 `public` profile permits (Brand Book, Visual identity, Business Model Canvas, Mascot atlas). The V3.2 and V3.3 modules are **internal**: SWOT/TOWS and the Value Proposition Canvas have no publishing document type, the journey map and SOSTAC overview are views of the marketing plan, and the OKR tree of the business plan, which the public profile refuses. They are scored and reported, not gated. Studio still renders a public edition of each (`/print?edition=public`), so their `redaction` check inspects that edition's fixture in en/fa/tr (no value in a non-approved state, no draft or internal badge) and requires the test that builds it; "the public profile refuses it" alone is not enough. None has reference screenshots yet, and SWOT, TOWS, VPC, CUSTOMER-JOURNEY-MAP, SOSTAC and OKR are unverified, so all five sit at 4.

Modules planned by later slices go in `PENDING_VISUAL_MODULES` (empty today). They are listed as **pending** and never fail anything; when a probe finds their code in `visual/` before they are declared, the report says "landed, not yet scored". A new module is added to `VISUAL_MODULES` with its builder, test files, catalogs, fixtures and evidence patterns.

### Standards verification

Every registry entry in `frameworks.json` has `verified_on` and `reviewer`. Both are recorded together, or both stay empty (`verified_on: null`, `reviewer: "pending"`). The claim rules refuse a date without a named reviewer, a reviewer without a date, and a date in the future. A date or reviewer is never invented. The V5.1 pass (2026-11-24) found that no source page had been checked by a person, so every entry is pending. To verify one, open `source_url`, confirm the title, publisher, edition and the part used, then set `verified_on` (that day) and `reviewer` (your name). The claim stays `informed_by` unless you choose a stronger one.

### Release gate

`npm run visual:gate` fails when:

- the registry or `release-gate.json` is invalid;
- a present **public** module scores below `public_min_score` (agreed threshold **4**: publication-safe);
- a module cites a framework that is not in the registry;
- with `--release`, or with `standards_block: "always"`: a cited external standard (`formal_standard` or `professional_framework`) has no `verified_on` and reviewer. Brand OS's own layouts (`editorial_template`) are reported but never block.

Without `--release`, unverified standards are printed as "would stop a release". CI (`validate` workflow, template repository) runs `npm run visual:gate -- --pilot`. Before a release, run `npm run visual:gate -- --release`. Internal modules are scored and reported but not gated.

**Owner override.** Only the owner edits `packages/brand-core/src/visual/release-gate.json`. Change `public_min_score` (0–5) or `standards_block`, or add an entry to `overrides`: `{ "target": "module:<id>" | "standard:<framework_id>", "reason": "…(≥ 10 characters)", "approved_by": "<owner name, never pending>", "approved_on": "YYYY-MM-DD", "expires_on": "YYYY-MM-DD" }`. An override turns that one failure into an "overridden by …" line. An override that has expired, is dated in the future, or has no named approver fails the gate. Agents never add an override.

### Cross-brand pilot

`runCrossBrandPilot` creates two **synthetic** brands (`fixtures-pilot.ts`: an English education brand without a mascot and a Turkish consulting brand with one; every value carries a `PILOT-A` / `PILOT-B` marker) through the normal init, answer, approve and publish path. It then builds the canvas, the identity chapter and the mascot atlas (internal and public), the Brand Book (internal and public), the Business Report and the Publishing gallery for both. It checks that:

- each document names its own brand, and no value crosses to the other brand;
- each internal Brand Book draws its own approved values;
- no public edition carries a draft;
- zones, block types and chapters are identical for both brands;
- the mascot chapter follows each brand's own module flag;
- the gallery grid is the same for both;
- no visual source file (outside fixtures) names a brand.

No real brand data is used or committed.
